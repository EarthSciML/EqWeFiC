This repo is an implementation of the WRF-(Chem) https://github.com/wrf-model/wrf and WRF-SFIRE (https://github.com/openwfm/WRF-SFIRE) models in .esm files. (Decided 2026-09-04: the fire code is NCAR's Community Fire Behavior Model, https://github.com/NCAR/fire_behavior, the `phys/fire_behavior` submodule of WRF 4.8 and the more recent, actively developed successor of the WRF-Fire/SFIRE line; WRF-SFIRE-only physics are optional later additions. See PLAN.md §1.)

WRF-... models are made up of process components that are composed together into the large-scale model. Implementation will take place in three stages.

In the first stage, the original fortran codes will be instrumented to output inputs and outputs from each model component during simulations. Outputs can either be instantaneous derivatives (preferred) or integrated trajectories over a time period. The code will also be instrumented to output inputs and outputs of subassemblies of components as appropriate. A select subset of these inputs and outputs will be used as tests in .esm stub files for each component or subassembly which will be added as pull requests to https://github.com/EarthSciML/EarthSciModels.

In stage 2, The stub .esm files will be filled in with the actual physics of each process so that the tests pass, then each PR will be reviewed by a human and merged. Then, the indvidual .esm components will be imported by reference into the subassembly .esm files and coupled together so that the subassembly .esm tests pass.

In stage 3, the components that have been merged into EarthSciModels will be imported by reference and coupled into top-level EqWeather.esm, EqAtmChem.esm, and EqAtmFire.esm models and tested against simulations of the full fortran models.

All model logic should be contained in .esm files. Tests and examples should be in the "tests" and "analysis" sections of .esm files, respectively. All local tests should be conducted using the EarthSciAST rust CLI binary, a copy of which should be kept untracked in the root directory of this repo.

The .esm files should be authored compositionally, with separate components, subcomponents, and expression templates used liberally and imported by reference into other components to keep the .esm code succint, simple, and human-interpretable. Avoid repeating logic or calculations, instead factor reused pieces into their own files/components/expression templates and import them by reference. Avoid the use of scripts to mechanically generate .esm files, as they often end up producing expressios that are not properly factored or succinct. (Scripts MAY be used to extract numeric test tuples from Fortran dumps into an existing hand-authored `tests` block, and to translate tabular data such as KPP `.eqn` reaction lists or lookup tables into `reaction_systems`, `function_tables`, or `data_sources` entries; the equations, structure, and factoring of a component are always authored by hand.)

Always, the equations in the .esm files should like like math rather than einsum operations whenever possible. For example, if a component includes a aggregate operation that is a numerical representation of a mathematical integral, the .esm equivalent should be written as an integral instead of a aggregate operation. Likewise, PDEs that are discretized in the fortran could should be written as PDEs, with discretization templates either used from or submitted as pull requests to https://github.com/EarthSciML/EarthSciDiscretizations.

Some components may already have implementations in EarthSciModels. If so, add additional tests from the instrumented FORTRAN to ensure the existing .esm implementations match their fortran counterparts.

Keep a centralized list of any bugs or errors that are found in the fortran code.

Do not store anything large in /tmp, as it is backed by RAM rather than hard drive and can cause an OOM.

Do not put "Co-Authored-By: Claude ..." in any commit messages. Claude is an LLM and LLMs cannot take responsibility for outputs, therefore they cannot be authors.

## Working conventions (added 2026-09-04 after the de-risking review; see PLAN.md for details)

- **Plan and inventory.** `PLAN.md` is the implementation plan. `INVENTORY.md` tracks every WRF scheme and sub-process with its stage status (`not started` / `instrumented` / `stub PR` / `physics PR` / `merged`). Update it whenever a component changes state. `FORTRAN_BUGS.md` is the centralized list of Fortran bugs required above.
- **Sibling repos.** Sibling checkouts in `../` are the working copies: `../EarthSciAST` (spec + Rust CLI source), `../EarthSciModels`, `../EarthSciDiscretizations`, `../WRF` (v4.8, shallow clone with `phys/physics_mmm`, `phys/noahmp`, and `phys/fire_behavior` submodules; remote `fork` = `ctessum-claude/WRF`, branch `earthsciml-instrumented`), `../WRF-SFIRE` (reference only). `.esm` `ref`s in this repo point at these sibling paths (relative), matching the convention used by `../simpleclimate.esm` and `../wildlandfire.esm`.
- **EarthSciModels commit trailers.** That repo's own `CLAUDE.md` (upstream commit b7912bc) forbids `Co-Authored-By: Claude ...` trailers, so commits on the `eqwefic/*` branches must not carry one (keep `Claude-Session:`). The same rule applies to commits in this repo (see the top of this file). Branches opened before 2026-09-07 still carry the trailer and should have it dropped the next time they are touched.
- **Fortran instrumentation lives outside this repo.** Kernel drivers and instrumented Fortran go in the forks `ctessum-claude/WRF` and `ctessum-claude/fire_behavior` (branch `earthsciml-instrumented`), not here. Push to those forks with `git -c credential.helper= -c 'credential.helper=!gh auth git-credential' push fork <branch>` over an `https://ctessum-claude@github.com/...` remote URL, because `~/.gitconfig` rewrites plain https GitHub URLs to ssh under the `ctessum` account. This repo holds only `.esm` files, the plan/inventory docs, and small extraction scripts under `tools/`. Large Fortran dumps go under `/projects/illinois/eng/cee/ctessum/ctessum/data/eqwefic/` (disk-backed), never in git and never in `/tmp`.
- **Test shape.** A component test is an esm §6.6 inline test. Inputs are `parameter_overrides` / `initial_conditions`; expected outputs are assertions on *observed* variables at `time: 0.0` (this is the "instantaneous derivative" form: tendencies are observeds, so asserting them at t=0 evaluates the RHS at the given state). Use a short `time_span` (e.g. `{start: 0, end: 1}`) for algebraic components, and an EMPTY one (`{start: 0, end: 0}`) when the document has ODE states but every assertion is at t = 0: esm-spec §6.6.2 names that shape, and the Rust runner answers it from the initial state without integrating anything, which on a large coupled document is the difference between one right-hand-side evaluation and a Jacobian over every state. Only use trajectory assertions when the Fortran component is itself an in-place time step that cannot be exposed as a rate. For Fortran schemes that do an implicit solve (e.g. PBL tridiagonal diffusion), generate the reference tendency with a small `dt` (≈0.01 s) so the implicit tendency approximates the instantaneous derivative, and say so in the test `description`.
- **A component does not own state a consumer will also drive.** Write the consumer-supplied column as a plain algebraic read (`x = input_x`) and expose the tendency as an *observed*; do not write `ic(x) = input_x` with `D(x) = dxdt`. A component that carries its own copy of the state binds only the INITIAL condition when a coupling document lowers `input_x` to a coupling-target parameter: it then integrates that copy under its own tendency alone while the document integrates the shared state under the sum of every scheme's, and the two diverge silently over a long run. YSU (theta, u, v, qv, qc, qi), Dudhia SW (T) and RRTM LW heating (T) were written the first way and converted on 2026-09-20; no count moved, because every assertion is at `time: 0.0` on an observed either way. The heating case shows the second cost: nothing in that component ever READ its `T`, so the only thing the ownership did was add 59 spurious ODE states to every document that mounted it. A component with no structural equation at all is fine — EarthSciAST #412 added the `static_evaluation_assertions` conformance category and Rust, Julia and Python all evaluate such a document once instead of integrating it.
- **An operator-split scheme joins an ODE document by exposing `increment / dt_substep` as an observed.** WSM6 is not a rate: it applies in-place increments over its own sub-step (melting/freezing, the budget rescaling, the saturation adjustment), and there is no rate hiding inside it to extract. The way in is to add, beside the existing `<x>_upd`/`<x>_out` state variables, an observed `d<x>_dt = (<x>_out - <x>_in)/dtcld` — which is exactly the tendency a consumer integrating the column must add, converges to the continuous process rates as the sub-step shrinks, and carries the scheme's own limiters at finite sub-step. It is a pure addition: the `_out` equations are untouched, so no existing assertion moves (790/790 for WSM6). Two things must be said out loud in the mounting document. The sub-step is a **parameter of the tendency, not the integrator's step** — prescribe it in the document and couple it into every stage, because a parent test cannot set a mounted component's parameter. And the result differs from the Fortran by O(dt_substep), because the Fortran stages its processes sequentially (each sees the state the previous one left) while a continuous formulation evaluates them all at one instantaneous state and sums; measure that difference, do not assume it is small. Done 2026-09-20 for `melting_freezing.esm`, `mass_conservation.esm` and `saturation_adjustment.esm`.
- **A component with no `index_sets` of its own still needs a bindable metaparameter.** Five WSM6 stages take `lev` entirely from a nested `sd`/`sat` subsystem and declared no `metaparameters` block, so a mount-edge `bindings` had nothing to bind and the leaf's default size won — `subsystem_index_set_conflict` the moment such a stage is mounted beside a column of a different size. Give the component an `NLEV` metaparameter whose only job is to be bound at the mount edge and passed down (`"sd": {"ref": ..., "bindings": {"NLEV": "NLEV"}}`). And check the `${ESD_ROOT}` grid imports at the same time: `sedimentation.esm` had `"bindings": {"NLEV": 40}` hard-coded on both of its ESD rule imports, which pins the grid regardless of the mount.
- **Column components.** Column physics is written over a vertical index set (`lev`, cell-based, N cells with N+1 edges) with consumer-supplied geometry (heights/pressures as shaped parameters), following the EarthSciDiscretizations convention that integer counts are metaparameters and real geometry is supplied by the consumer. Vertical diffusion, vertical flux divergence, and column integrals are written as continuous operators (`D` wrt `lev`, `integral`) and lowered by rules imported from EarthSciDiscretizations; missing rules are added there by PR first. Discrete recurrences (esm §4.3.1.1) are reserved for genuinely sequential sweeps (e.g. two-stream radiative transfer up/down passes) and must be justified in the component description.
- **Constants.** Every WRF constant comes from `lib/wrf_constants.esm`, mounted as a subsystem (`"subsystems": {"wrf": {"ref": "../../lib/wrf_constants.esm"}}`) and referenced by the bare mount name (`"wrf.cp"`) in both equations and test assertions (decided 2026-09-15). Do not use the model-qualified form (`"<Model>.wrf.cp"`): it is not rewritten when the component is mounted under a different key, so a component written that way can only be mounted under its own model name. It is (transcribed from `share/module_model_constants.F`, plus per-scheme parameter files where a scheme redefines a constant). Never write a physical constant inline in a component. **A conversion factor carries the units of the conversion, never `"1"`** — `degrad` is `rad/deg`, not dimensionless — even when the Fortran it is transcribed from carries no units. Since EarthSciAST #413 (2026-09-19) the transcendentals apply the declared *scale* of their argument, so a `deg`-typed expression handed to `sin`/`cos` is converted again: declaring the factor dimensionless silently double-converts every angle built with it (this broke 17 assertions in the solar geometry; see PLAN.md §3.1). Hand a trig function either a quantity declared `deg` (unscaled) or one declared `rad`.
- **Tolerances.** Reference values from single-precision WRF builds use `rel: 1e-5`; from double-precision kernel builds (`kind_phys` = real64, preferred when the harness allows it) use `rel: 1e-9`. State which build produced each test's values in its `description`.
- **Do not merge red tests.** EarthSciModels CI runs every inline test on every push and the test schema has no skip/xfail marker. Stage-1 stub files therefore live on a branch of this repo (`components/` mirrored to the EarthSciModels layout) and are opened as EarthSciModels PRs only once their tests pass in stage 2. Stage-1 PRs to EarthSciModels are limited to additional tests for components that already exist there.
- **Coupled assemblies live in `couplings/`** (EarthSciModels' directory for coupled documents), not under `components/`, and are run as `./esm test couplings/<file>.esm` or over the whole directory. The `--model <AssemblyModel>` selector this rule used to require is obsolete since EarthSciAST #214 (2026-09-08): a mounted component's inline tests no longer run under the coupling, so a whole-directory run no longer goes red.
- **Local test command.** `./esm test <file-or-dir>` (Rust CLI; rebuild from `../EarthSciAST/pkg/earthsci-ast-rs` with `cargo build --release` when the spec moves). (The pin to `d7ad059d3` is LIFTED: EarthSciAST #432 was fixed by #434 and #433, both merged 2026-09-20, and `main` at `3cf6f6f92` is green on this corpus.) **A whole-repo run takes ~20 minutes EXCEPT for `couplings/eqweather_scm.esm`, which against EarthSciAST `main` at `3cf6f6f92` is 1 h 51 m by itself** (measured 2026-09-20: 110 m 36 s for ONE right-hand-side evaluation, on an empty time span, so nothing is integrated). The cause is **EarthSciAST #438, fixed in PR #439.** The Rust driver built a diffsol problem and an implicit solver for EVERY run, including one that cannot advance — an empty `time_span`, or a non-empty one whose whole output grid sits at `t0`. Constructing an implicit solver materialises the Jacobian, and that crate's is a matrix-free finite-difference JVP, so it is called once per state column and each call evaluates the entire RHS twice: **2·n_states + 1 full evaluations** to return the untouched initial state. What costs is the STATE COUNT, not the recurrence: a 103-deep self-referential sweep with no state runs in 0.03 s, the same sweep with ONE scalar state it depends on in 0.09 s, and the same sweep over 103 states in 1.84 s. Repros: `data/eqwefic/phase3_probes/mwe_state_leaf_{static,ode}.esm`. **With #439 the same document is 2 m 31 s and the same 65/65**, so when it merges, rebuild `./esm` from `../EarthSciAST` and re-time the whole repo. **Updated 2026-09-20 after WSM6 was mounted:** the document now carries two tests (clear-sky step 1410 and cloudy step 60) over 656 states and 24 mounts, and takes **7 m 58 s for both on the #439 binary** (3 m 47 s for the clear-sky test alone). On `main` it is WORSE than before — the state count went 479 → 656, so #438 charges 2·656+1 = 1313 full RHS evaluations per run instead of 959; a run was killed unfinished at 15 minutes. **The repo's `./esm` is NOT necessarily the #439 build** — check its mtime against `../EarthSciAST/pkg/earthsci-ast-rs/target/release/esm` before timing anything, and note which binary produced any number you report — the same defect was charging every test written in the standard `{start: 0, end: 1}` shape with assertions only at `time: 0`, which is most of them. So: `./esm test .` is ~2 hours and `./esm test couplings/` is ~1 h 50 m, while every other directory is unchanged. It STAYS in the suite (decided 2026-09-20) — always run the whole repo in the background, and when only other files were touched, check them by directory first and let the full run confirm. **Any OTHER document that runs for hours is still the regression, not a big suite.** Always run it line-buffered (`stdbuf -oL ./esm test ... | grep ...`) or piping through `grep` will block-buffer and hide all progress until the run ends. **`ESD_ROOT` must be exported first** — `export ESD_ROOT=/projects/illinois/eng/cee/ctessum/ctessum/code/EarthSciDiscretizations` — because EarthSciDiscretizations rules are referenced as `${ESD_ROOT}/grids/...` (esm-spec §4.7 env-var ref expansion, EarthSciAST #400). When the variable is unset the loader deliberately leaves the literal token in place so the ref fails unresolved, and every file importing an ESD rule reports `template_import_unresolved` rather than a test failure. Run tests with the Rust CLI only. The EarthSciModels CI gate (`tools/run_esm_inline_tests.py`, Python binding) is a condition for *merging* an EarthSciModels PR, not for creating one, and its slowness on array operations is a Python-binding performance issue handled separately; do not run it as part of this work. Run a test in the Julia or Python binding only to debug a case where the Rust CLI itself appears to be wrong.
- **Existing components take precedence.** Before authoring a component, search `../EarthSciModels/components` (and `lib/`) for an existing implementation (e.g. Monin-Obukhov surface layer, Holtslag-Boville PBL, saturation vapor pressure, Rothermel/level-set fire spread). Reuse by reference and add WRF-derived tests rather than duplicating.
